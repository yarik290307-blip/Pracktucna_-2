1. Що таке інкапсуляція? Наведіть 5 різних прикладів з вашого коду. Інкапсуляція — це один із базових принципів об'єктно-орієнтованого програмування, який полягає у приховуванні внутрішнього стану об'єкта від прямого доступу ззовні та наданні доступу до нього лише через спеціальні методи або властивості (гетери та сетери). Це захищає дані від некоректних змін. Приклади з мого коду:
1.	Приховування поля _fullName у класі Student (поле private, доступ лише через властивість FullName, де йде перевірка на довжину).
2.	Прихований список студентів private List<Student> _students; у класі StudentGroup. Додавання чи видалення можливе лише через методи AddStudent та RemoveStudent.
3.	Словник оцінок private Dictionary<string, double> _grades; у класі GradeJournal. Доступ реалізовано лише через метод AddGrade.
4.	Властивість AverageGrade у класі Student має публічний get, але приватний set. Тобто прочитати бал можна вільно, а змінити — лише зсередини класу (наприклад, через метод UpdateAverageGrade).
5.	Властивість Age має лише блок get (read-only), вона обчислюється на основі дати народження, і змінити вік "вручну" ззовні неможливо.
2. Порівняйте авто-властивості та властивості з повною реалізацією. У яких випадках ви обирали кожен варіант?
•	Авто-властивості (наприклад, public string Notes { get; set; }) не мають явно заданого приватного поля — компілятор створює його автоматично "під капотом". Їх я використовував тоді, коли дані не потребують жодних перевірок чи трансформацій при записі та читанні (нотатки можуть бути будь-якими).
•	Властивості з повною реалізацією (наприклад, FullName) мають окреме приватне поле (backing field) та розгорнуті блоки { get { ... } set { ... } }. Я використовував їх тоді, коли перед записом даних у поле потрібно виконати бізнес-логіку — наприклад, перевірити, чи не порожній рядок, чи відповідає він формату (валідація).
3. Для яких даних ви застосували валідацію? Які види валідації використовували? 
Валідація застосовується в сетерах властивостей, і в разі помилки викидається виняток ArgumentException:
•	FullName: перевірка на те, чи рядок не є порожнім/не складається лише з пробілів (string.IsNullOrWhiteSpace), а також перевірка мінімальної довжини (мінімум 5 символів).
•	RecordBookNumber: перевірка на наявність рівно 8 символів (value.Length != 8).
•	PersonalEmail: базова перевірка формату — наявність символів @ та . у введеному рядку.
•	AverageGrade: у методі UpdateAverageGrade реалізована перевірка діапазону (оцінка має бути від 0 до 100).
4. Навіщо потрібні read-only та init-only властивості? Приклади з коду.
•	Read-only властивості мають лише блок get. Вони потрібні для даних, які генеруються або обчислюються самим об'єктом, і користувач не повинен їх змінювати вручну. Приклад: властивість GroupSize у StudentGroup просто повертає _students.Count.
•	Init-only властивості (init замість set) дозволяють задати значення властивості лише один раз під час ініціалізації (створення) об'єкта. Далі вона стає доступною лише для читання. Приклад: EnrollmentDate (дата зарахування). Студента зараховують один раз, і ця дата не має змінюватися в процесі навчання.
5. Поясніть роботу властивості Age. Чому вона обчислювана? 
Властивість Age не має власного поля для зберігання. Щоразу, коли ми звертаємося до student.Age, виконується блок коду в get, який віднімає рік народження від поточного року. Далі йде перевірка: якщо день народження в поточному році ще не настав, вік зменшується на 1. Вона є обчислюваною, оскільки вік — це динамічна величина, яка змінюється з плином часу. Якби ми зберігали вік як звичайну цифру, нам довелося б писати окремий скрипт, який би щодня перевіряв усіх студентів і оновлював їм вік, що є неефективним і створює ризик неактуальних даних.
6. Як ви реалізували принцип єдиної відповідальності (SRP) в класах? Кожен клас відповідає суворо за свою частину логіки:
•	Клас Student нічого не знає про групу чи меню, він відповідає виключно за збереження та валідацію даних одного конкретного студента.
•	Клас StudentGroup відповідає лише за колекцію студентів (додавання, пошук, фільтрація, робота з файлом), але не взаємодіє з консоллю.
•	Клас GradeJournal відповідає виключно за збереження оцінок з дисциплін та перерахунок середнього бала.
•	Клас Program містить лише користувацький інтерфейс (UI) — вивід меню, читання з клавіатури, обробку винятків.
7. Які труднощі виникали під час проєктування архітектури? Як вирішували? 
Головною складністю було зберегти інкапсуляцію списку студентів у класі StudentGroup, але водночас надати можливість виводити їх у консольному меню Program.cs. Якщо зробити список _students публічним, це порушить інкапсуляцію і дозволить іншим класам неконтрольовано очищати чи змінювати список. Рішення: Було залишено приватне поле _students, але додано публічний метод GetAllStudents(), який просто повертає посилання на існуючий список для читання та ітерації в меню.
